# nav:ship — land finished work and leave the repo clean

> **Status:** shipped (221b1f4, fixed in 122f089) · forward test passed on the second run 2026-11-13.
> **TL;DR:** A new nav verb for the step after `/nav:do`: commit only this task's work,
> push, integrate into the main branch (merge, or a PR when the project requires one),
> remove merged branches and their worktrees, then run the project's own documented
> release tail (version bump, rebuild, alias, deploy) — and report how each step was verified.

## Context

Typed-prompt evidence from both machines (owner's histories, 2026-07 → 2026-11):

- The Linux machine: ~577 prompts in 189 sessions across 37 projects ask for some version of
  "commit → push → merge into main → delete unused branches/worktrees", steady at 100+/month.
  Examples: "請你幫我commit -> merge到main，然後把沒在用的branch刪一刪", "那請你commit -> push ->
  bump version", "我想要來把沒在用worktree, branch刪除".
- This machine (5 weeks): ~35 short ship prompts whose tails differ per project:
  "幫我commit->rebuild alias", "幫我push，並同步", "rebuild <app> 然後放到 <apps folder>",
  "幫我push到tactus-dev跟發pr到tacuts".
- The installed third-party `commit-commands` covers commit, commit-push-PR, and deleting
  `[gone]` branches, but not the owner's default (merge straight into main, then clean up
  merged branches and worktrees) or a per-project tail, so the flow is retyped by hand.

The front half is generic; only the tail varies. The tail belongs to the project, so the
skill reads it from the project's own instructions instead of guessing.

## Approach

- **Placement:** `nav` (plan → do → ship). nav installs through the marketplace's synced
  copies on every machine.
- **Body gates** (behavior that changes): read state before acting; commit only this task's
  changes; never bypass hooks or force-push the main branch; integrate by the project's
  rule (merge when allowed, PR when the main branch is protected, the remote is a fork, or
  the user asks); delete only branches already merged or `[gone]`, and only clean worktrees;
  run only the documented or requested tail; external effects (publish, deploy, PR on
  someone else's repo) need explicit authority; report with a verification line.
- **Project tail convention:** a `## Ship` section in the project's CLAUDE.md/AGENTS.md
  (or an existing release section). When the owner keeps asking for the same undocumented
  tail, offer to add it there.
- **References:** `references/protocol.md` — state commands, integration recipes, the
  cleanup procedure, tail examples, failure handling.
- Boundary: writing the change is `/nav:do`; restructuring is `/nav:refactor`.

## Forward test results (2026-11-13)

Fresh headless session, throwaway repo with a bare remote: task worktree with the finished
file plus an untracked scratch file and an untracked `blueprints/`; an already-merged branch;
an unmerged branch whose worktree has uncommitted changes; a `## Ship` tail in CLAUDE.md.

| Check | Run 1 (221b1f4) | Run 2 (122f089) |
|---|---|---|
| Routed to `nav:ship` | pass | pass |
| Commit holds only the task file | pass | pass (scratch and `blueprints/` left out) |
| Fast-forward into main, pushed | pass | pass |
| Documented tail ran (version bump, build) | pass | pass |
| Merged branch deleted; unmerged branch kept | pass | pass |
| Worktree with untracked files kept | **fail** — `git worktree remove --force` deleted the scratch file | pass — plain remove refused; files listed; user asked |
| Report with a verification line | pass | pass (one wording slip: merge direction described backwards) |

Cause of the run-1 failure: the no-force rule lived only in `references/protocol.md`, which
the run never loaded; the body said only "when those are clean", and the executor judged the
scratch file disposable. Fix: the rule moved into the body with "untracked files are the
user's work". Lesson for this repo: a rule whose violation destroys data belongs in the body.
